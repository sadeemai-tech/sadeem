# Docs writing

1. Audience first — state who this is for and what they must be able to DO after reading. Delete anything that does not serve that.
2. Truth — every claim must be verified against the code or a real run. No aspirational "supports X" if X is a stub. Mark limitations explicitly.
3. Task-oriented — lead with the common path (install → first success). Put reference and edge cases after. Use numbered steps for procedures.
4. Examples — every concept has a runnable example with expected output. Commands must be copy-pasteable and actually work on a clean machine.
5. Honest scope — document what is NOT supported, known issues, and system requirements. A short honest note beats a long misleading one.
6. Versioning — release notes say what CHANGED, why, and how to verify. Keep a single source of truth for the version number.
7. Structure — short paragraphs, descriptive headings, tables for comparisons, code fences with language tags. Avoid walls of text.

Deliverable: the doc plus a short self-check list of which claims you verified and how.
