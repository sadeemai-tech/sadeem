## 1. Verdict / الحكم — blunt / بصراحة

**EN:** The 429 fix **works functionally**. All four acceptance criteria pass against the REAL engine with a scripted mock provider. 429s are absorbed in place on the user's own provider, the task continues to completion, tools are never re-executed, and the run never auto-switches. The "founder's 303s 429 FAIL" class of failure is gone for N=3..6 bursts.

**AR:** إصلاح 429 **يعمل وظيفياً**. كل معايير القبول الأربعة نجحت مع محرك حقيقي ومزود وهمي مبرمج. الـ 429 يُمتص في نفس المزود، والمهمة تكتمل، والأدوات لا تُنفَّذ مرتين، ولا يحدث تبديل تلقائي للمزود. فئة فشل "303 ثانية ثم فشل 429" اختفت لدفعات N=3..6.

**BUT / لكن:** one **honesty defect remains** — a wording lie in the terminal error. It says "trying the next configured model" while the code explicitly refuses to switch. See §5. Non-blocking, but it is a lie to the user and should be fixed.

## 2. Method / المنهج

- `electron/agent/engine.ts` and `electron/agent/providers.ts` are **bundled from live source at test call time** via esbuild (same posture as `tests/v1111-antifreeze.test.mjs`). `electron` is stubbed to a plain-Node `app.getPath -> userData`.
- A loopback-only `node:http` OpenAI-compatible SSE provider serves scripted steps: `h429()`, `hStatus(402/401)`, `hTool(write_file)`, `hText(...)`.
- Settings deliberately configure **two providers with credentials** AND set `agent.allowModelFailover = true`. This makes "no auto-switch" a strong assertion: a switch would show up as a request for a different `body.model`.
- Recording IO auto-allows every permission and can abort from inside `send()`.
- Env (matches production defaults except the deliberately accelerated engine backoff):
  `SURNIA_RATE_LIMIT_MAX_ATTEMPTS=8`, `SURNIA_RATE_LIMIT_BUDGET_MS=60000`, `SURNIA_TURN_RETRY_DELAYS_MS=10,10,10,10,10,10`.
  The accelerated turn delays are a tripwire: if the engine ever fell back to its own retry schedule, requests would multiply and the exact-count assertions would fail. They never fired in any 429 path.
- No skips on Windows. No app source touched.

## 4. Failure list / سجل الفشل

**App source failures: NONE.** No `file:line` defect found in the 429 path under these scenarios.

**Test-harness issue found and fixed (not an app bug):** the first run showed `journalReports=0` for every scenario. Cause: journal events are async/debounced (`JOURNAL_FLUSH_MS=120`, `electron/agent/journal.ts:96`) and my reader ran before the flush. Added a 50 ms poll (up to 1 s) in the harness; all journal counts then became exactly 1. This is a test-timing artifact, not a product defect.

**Honesty defect (source, non-blocking):** see §5.

## 5. Residual defect — wording lie / عيب لغوي متبقٍ

`electron/agent/engine.ts:6436` and `electron/agent/providers.ts:705` both emit:

> `Rate limited (429) — trying the next configured model.`

On exhaustion the engine **does not** try another model — `electron/agent/engine.ts:5288` breaks out of the failover loop, and `electron/agent/engine.ts:5267` breaks out of the retry loop. The terminal report therefore tells the user something the app explicitly refuses to do. Functionally correct, textually false. Recommend rewording to `Rate limited (429) — waiting briefly / try again shortly.` **I did not change source.**

## 6. Implementation anchors / مواضع التنفيذ (as verified)

- `electron/agent/providers.ts:766` — `rateLimitMaxAttempts()` (default 8, clamped 1..50).
- `electron/agent/providers.ts:773` — `rateLimitBudgetMs()` (default 60,000 ms).
- `electron/agent/providers.ts:966-1008` — the 429 branch: in-place retry on the SAME request, exponential 250→500→1000 ms capped ≤1 s, one quiet notice at `providers.ts:982-987`, terminal error at `providers.ts:998-1004`.
- `electron/agent/providers.ts:1454/1464` and `2038/2044` — `maxRateLimitRetries` threaded into both wire protocols.
- `electron/agent/providers.ts:2471` — explicit-failover callers still get the legacy 1-retry cap.
- `electron/agent/engine.ts:5190` — provider notices routed to the engine's deduped `sys_notice` channel.
- `electron/agent/engine.ts:5267` and `5288` — rate-limit exhaustion stops retry AND stops failover (no auto-switch).
- `electron/agent/engine.ts:6363` — `isRateLimitExhausted()` classifier.

## 7. Caveats / تحذيرات

1. **The bound is the attempt cap, not the 60 s budget.** With 8 attempts and ≤1 s waits the worst case is ≈5.75 s (verified 5.83 s). If the founder wants to ride out a longer congestion episode, raise `SURNIA_RATE_LIMIT_MAX_ATTEMPTS` (hard ceiling 50) — the 60 s budget then becomes the real cap.
2. **Concurrent edits.** F2 was editing `providers.ts`/`engine.ts` while this verification ran (mtimes 16:40–16:42). I re-ran twice after the edits landed; both runs were 11/11. The verdict reflects the source at those two runs only.
3. **What was not tested:** real vendor 429 bodies with `Retry-After: 30` (the code caps the wait at 1 s but keeps the raw seconds as a hint; only the no-header exponential path was exercised here), and authenticated multi-account failover. Not claimed as verified.
4. **"One written report"** was verified both as one `task_report` event and as one journaled `task_report` row.

## 8. Bottom line / الخلاصة

**EN:** Ship the 429 recovery. It does what the founder asked: continues the same task on the same provider, no duplicate tool execution, one quiet notice, one honest report, bounded failure. Fix the misleading "trying the next configured model" string before release.
