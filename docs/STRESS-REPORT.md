## 3. What each stress test proved

### 3.1 STREAM CONTINUITY — 15 real engine turns (PASS)
Five token speeds per run, repeated 3×: **10, 50, 200, 700, 2000 ms per token**.

Per-turn checks (all passed every time): first `think_delta/text_delta` arrived
within the load-adaptive 6 s model→first-token budget (observed **205–572 ms**);
no token gap exceeded the configured idle/watchdog window (largest observed gap
**~753 ms** at 700 ms/token; 0 ms at 2000 ms/token because the slow stream was
batched to one event per phase); no `error`, no `aborted`, no notice matching
`watchdog|stream stalled|stream interrupted|disconnected|no model activity`;
`task_report` present and followed by `turn_end`; post-stream lag from last token
to `task_report` was **45 ms – 2007 ms** (well inside budget); ≥2 real provider
round-trips each turn.

### 3.2 LONG RUN — 12 real tool calls across a REAL compaction (PASS)
One engine turn: **6 × `write_file` + 6 × `run_command`** executed through the
real tools layer, then a final answer. A genuine engine auto-compaction was
forced (mock reported `prompt_tokens: 200000`; the engine's 65 % threshold for
the 200 k fallback window is 130 000, and `compactThreshold: 10000` created a
real head/tail split). Observed in every run:

- `compaction=1`, heartbeat phase `compacting` present mid-run, 14 provider requests.
- `12` `tool_start` and `12` ok `tool_result`; tool-call IDs matched one-to-one
  (no dropped tool message).
- 13 `text_delta`s; the final answer contained **all 6** written file paths and
  "All done."; all 6 files verified on disk.
- no error/abort/stall; `task_report` + `turn_end` emitted.

### 3.3 TOOL STORM — every registered tool (PASS)
**The live registry has 145 tools, not the 142 in the task brief** (verified via
`tools.getToolDefs([])`). The harness dispatches *all* of them, so "all 142" is a
strict subset of what was exercised. Two rounds (284→**290** dispatches with the
145-tool registry): `{}`/allow plus schema-derived minimal args in auto-denied
(simulated read-only) mode with `fullAccess:false` and a sandbox workspace;
slow/network/background tools forced to `{}` so they refuse honestly and fast.

Result, identical in all 3 runs: **ok=50, honest-refusal=240, unknown=0,
uncaught throws=0, invalid-JSON=0, other failures=0.** Two tools (`env_probe`,
`env_manager`, schema-minimal round) shell out to `nvm list` and take ~8–16 s;
they still return honest outcomes and are the bulk of the storm's runtime.

### 3.4 MALFORMED EVENTS — 500 seeded-random events (FAIL — real bug)

## 5. REAL FAILURE — reproduction and exact source location

**Symptom:** `TypeError: steps.join is not a function` thrown synchronously from
`ingestAgentEvent`. This is the single renderer-side choke point for the entire
agent stream; a throw here loses the current event's state update (buffered
deltas may never flush → "thinking stops" / "no response") and can repeat on
later events — the exact symptom family the founder is trying to eliminate.
The v11.14 hardening comment at `src/store.ts:2996-3001` explicitly promises a
malformed event "must NEVER throw here" — this violates that invariant.

**Exact source line:** `src/store.ts:3287`
```
3286:  const steps = e.steps ?? (e.title ? lines : lines.slice(1));
3287:  const planBody = raw.trim() || steps.join('\n');
```
`e.steps` is taken from the untrusted IPC payload without an array check; a
non-array value makes `.join` throw. (`steps.length` at line 3291 would also be
wrong for a non-array.) Reproduced in the `case 'plan_ready'` block,
`src/store.ts` lines **3275–3307**.

**Minimal deterministic reproduction** (renderer store must have a session
loaded, as `seed()` does in the harness):
```js
const { useStore } = require('<bundle of src/store.ts>');   // with window.surnia + localStorage stubs
useStore.setState({ session: { id:'s1', messages:[], /* ... */ }, running: true });
useStore.getState().ingestAgentEvent({
  type: 'plan_ready',
  steps: 1,                 // <-- non-array "steps" from untrusted IPC
});
// -> TypeError: steps.join is not a function
//    at src/store.ts:3287 (case 'plan_ready')
```

**Exact fuzz event that triggered it** (index #242, deterministic across runs):
```json
{"type":"plan_ready","text":0,"message":[{"nested":225.8269942831248},0.5659601918887347],"output":0,"steps":1,"n":161.5877179428935,"stopReason":"xxxxx"}
```

**Harness reproduction command:**
```
node --test --test-force-exit --test-name-pattern="MALFORMED-EVENTS" tests/v1115-stress.test.mjs
```

**Suggested fix (for the parent / engine owner — NOT applied here):** coerce and
validate before use, e.g.
`const steps = Array.isArray(e.steps) ? e.steps : (typeof e.steps === 'string' ? [e.steps] : (e.title ? lines : lines.slice(1)));`
and guard `.risks` similarly. This keeps the forward-compatible "never throw"
contract honest.
